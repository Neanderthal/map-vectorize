# Автоматическая привязка растровых геокарт (без ручных точек)

> Исследование от 2026-10-05. Вопрос — найти МЕТОД полностью автоматической
> геопривязки сканов ГГК-1000/3 (советские 1:1 000 000, видоизменённая
> поликоническая проекция, кириллица) без ручного снятия точек; только
> open-source, локально, Python. Метод: fan-out веб-поиск по 5 углам → 19
> источников → 92 утверждения → состязательная проверка 25 (3 голоса, 2 «против»
> убивают) → синтез. Подтверждено 22, опровергнуто 3.
>
> Уровень доверия и итог голосования указаны у каждого пункта. Все цифры точности —
> границы класса метода из статей, НЕ замеры на наших листах.

## Главный вывод

Полностью автоматическая привязка таких листов — **решённая задача**. Канонический
рецепт (Gede & Varga, Proc. ICA 4:38, 2021; e-Perimetron 17/4, 2022):

> **детектировать рамку/углы листа (OpenCV) → распознать номенклатуру листа
> (Tesseract/pytesseract) → вывести координаты углов из номенклатуры детерминированно
> → отдать GDAL как GCP.**

Весь стек Python + OpenCV + Tesseract + GDAL, локально, без облака; 1147 листов по
~4 c/лист. (доверие: высокое)

**Геодезическое основание** (Snyder, USGS PP 1395; доверие: высокое, 3-0): для
разграфки IMW/СССР 1:1 000 000 точные координаты углов выводятся из обозначения листа
**аналитически, карту читать не нужно**. Размер рамки задан широтным поясом: 6°×4°
между 60°N и 60°S; **12°×4° между 60° и 76°N** (двойные листы — ровно случай
`P-(35),36`); 24°×4° между 76° и 84°.

## Три семейства методов и вердикты

### 1. Рамка + OCR номенклатуры → GCP (Gede & Varga) — БЕРЁМ ЗА ОСНОВУ

- **Алгоритм детекции рамки** (доверие: высокое, 3-0): бинарная маска «чёрного»
  (разброс каналов R,G,B < 25% и среднее < 50%) → вероятностное Hough-преобразование
  (линии длиннее ¼ ширины изображения) → разделение почти-горизонтальных и
  почти-вертикальных по азимуту с допуском 5° (компенсация перекоса скана) →
  пересечения = грубые углы → уточнение свёрточным ядром (максимум свёртки).
  *Примечание: нижнюю рамку обычный Hough не находил (мешала линейка масштаба) —
  понадобился отдельный шаг.*
- **Чтение номенклатуры** (доверие: высокое, 3-0): обрезать область над верхней
  рамкой → `pytesseract.image_to_string` (настройки по умолчанию) → валидация ID
  регулярным выражением по шаблону разграфки. Успех OCR — **75,9%** (самое слабое
  звено), лишь 1,4% прочитаны с ошибкой сверх автокоррекции.
- **Метрики класса** (доверие: высокое, 3-0): ошибка детекции углов <1% размера листа
  для 89% листов, <2% для 99%. ⚠️ Бенчмарк — венгерские 1:25 000 Gauss-Krüger, НЕ на
  ГГК-1000 поликонике.
- **Валидация на советских параметрах** (доверие: высокое, 3-0): метод тестирован на
  серии с Gauss-Krüger / Pulkovo 1942 / эллипсоид Красовского и той же
  IMW-производной логикой номенклатуры (родительский квадрант 6°×4° = лист 1:1М).
  Вывод углов из ID **проекционно-независим**.

**🔴 Ключевое ограничение для проекта** (доверие: высокое): метод Gede предполагает
приблизительно **прямоугольную** рамку и использует **только 4 угла + аффинную/
проективную** привязку. У ГГК-1000/3 рамка **трапециевидная с дугами параллелей** → 4
угла дадут корректные координаты углов, но **перекос к краям** (ровно проблема «bbox по
углам», от которой предупреждает `pipeline.md`). Лечение — **GCP по узлам градусной
сетки** вместо 4 углов. Переносимая часть метода — концепция автоматизации
(OCR ID → вывод рамки → авто-GCP → без ручных точек); шаг «только 4 угла» заменяем.

### 2. OCR подписей координат сетки (Tyagi & Dubey, NCVPRIPG 2025) — ЛУЧШЕ ДЛЯ ТРАПЕЦИИ

(доверие: высокое, 3-0) EasyOCR + двухстадийный мультимодальный LLM разбирают печатные
подписи широты/долготы (degree-minute-second) → аффинная подгонка с RMSE-отсевом
выбросов → GCP → GeoTIFF (EPSG:4326). Код: `github.com/pallavi093/OCR_LLM_Georeferencing`.
Метрики (доверие: среднее, 2-1): внутренний RMSE <5 м, валидационный RMSE <30 м на 11
из 12 листов, <350 c/лист.
**Плюс для нас:** GCP ставятся там, где есть подписи сетки (а не только в углах) →
лучше ложится на трапециевидную рамку. **⚠️ Оговорки:** цель — Survey of India 1:50 000
с прямоугольной сеткой; мультимодальный LLM может требовать облачного API (противоречит
нашему «только локально»); цифры самоотчётные.

### 3. Feature-matching и со-регистрация — ТОЛЬКО УТОЧНЕНИЕ, НЕ ХОЛОДНЫЙ СТАРТ

- **Vaienti et al. 2025** (доверие: высокое; 3-0/2-1): перенос GCP с уже привязанной
  опорной карты (Anchor) на новую через SuperPoint + SuperGlue + RANSAC + проверка
  триангуляцией Делоне. RMSE <1% диагонали в 78,1% случаев. Код:
  `github.com/BeatriceVaienti/georeferencing_propagation`. 🔴 Требует заранее
  привязанной похожей перекрывающейся карты — не решает холодный старт.
- **AROSICS** (доверие: высокое, 3-0): субпиксельная со-регистрация двух **уже
  геокодированных** растров фазовой корреляцией. «does not georeference raw,
  unprojected imagery» — только уточнение.
- **Milleville et al. 2022** (доверие: высокое, 3-0): OCR **топонимов** + геокодер →
  область интереса → 4 угловых GCP. Ошибка 316 м (1,67%) на историч., 287 м (0,90%)
  на совр. картах. ⚠️ Авторы прямо пишут: OCR «too error-prone on cluttered, highly
  detailed topographic maps»; геокодер (Nominatim) — внешний сервис.

## Что это значит для нашей архитектуры

Рецепт-основа подтверждён, и наши выводы совпали с литературой:
- Углы — **из номенклатуры детерминированно** (не читаем карту).
- 4-угловой аффин **недостаточен** для коники → нужны **GCP по узлам сетки** (как уже
  прописано в `pipeline.md` и как я построил из детектированных дуг).
- Feature-matching/AROSICS/топонимы — максимум как **финальное уточнение/проверка**,
  не как старт.

Отсюда — наша схема **слияния сигналов**: A (номенклатура→углы) + B (детекция сетки→
узловые GCP) + C (OCR подписей градусов) + D (гидрография ↔ опора как проверка).

## Важные оговорки (проверено)

1. **Ни один метод не валидирован именно на ГГК-1000 в поликонике.** Все цифры (<1%
   углов, RMSE <30 м, 316 м) — границы класса, не замеры на целевых листах.
2. **Точная математика видоизменённой поликоники НЕ подтвердилась** — формулы Snyder
   §18 (радиусы дуг параллелей, уравнения 18-23…18-35) отклонены голосованием (0-3 и
   1-2). Вывод: **не опираемся на аналитическую проекцию**; опираемся на
   детектированные дуги + эмпирическую проверку.
3. **Готовой open-source детекции именно внутренней градусной сетки** (а не рамки) для
   поликонических листов в подтверждённых источниках **не найдено** — наш детектор дуг
   закрывает этот пробел сам.
4. Два метода **нарушают «только локально»**: мультимодальный LLM (Tyagi & Dubey) и
   геокодеры (Milleville). Для локальности нужен self-hosted LLM / локальный Nominatim —
   не доказано в источниках.
5. **Надёжность кириллического OCR** номенклатуры/подписей на перегруженных 1:1М листах
   с оверпринтом — открытый вопрос (75,9% — на чистых топокартах).

## Открытые вопросы

1. Точная математика видоизменённой поликоники IMW (Snyder §18) — даёт ли closed-form
   построение полной сетки GCP из граничных параллелей и центрального меридиана? (claims
   отклонены — нужна отдельная проверка по первоисточнику).
2. Есть ли готовая open-source автодетекция внутренней градусной сетки (не только
   рамки), пригодная для трапециевидных поликонических листов?
3. Реальная доля успеха Tesseract/EasyOCR на кириллической номенклатуре/подписях
   перегруженных ГГК-листов (vs 75,9% на чистых).
4. Можно ли LLM (Tyagi & Dubey) и геокодер (Milleville) запустить полностью локально
   без потери точности?
5. Есть ли привязанный опорный растр/вектор района (Ладога/Онега, OSM/Natural Earth/
   GSHHG) для feature-matching/кросс-модальной проверки как финального шага?

## Опровергнутые утверждения (для протокола)

| Утверждение | Голоса | Источник |
|---|---|---|
| В видоизменённой поликонике все меридианы — прямые (не сходятся в полюс), 2 меридиана ±2° от центрального истинны по масштабу | 1-2 | Snyder §18 |
| Параллели — неконцентрические дуги с радиусом R=a·cot(φ)/… (18-26), closed-form отображение 18-23…18-35 | 0-3 | Snyder §18 |
| Полностью авто-конвейер строится в Python только на OpenCV+Tesseract+GDAL — именно стек map-vectorize | 1-2 | ICA-Proc 4:38 (как тривиальный вывод) |
